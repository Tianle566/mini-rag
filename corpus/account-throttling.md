# 同一个模型，为什么有的账号就是慢

> 一次跨三层的排查复盘：从面板日志，到上游逐单日志，到逐 chunk 探针。
> 结论先说：**"慢"不是一种病，至少是三种。分清它们之前，任何优化都是在猜。**

## 一、起点：体感和数据对不上

现象很朴素：同一个模型（deepseek-v4.1-flash）、同一个客户端、同一个推理档位，甲账号 5 秒出结果，乙账号 12 秒。

更奇怪的是——**甲账号在过去 5 分钟里接的单反而更多**。

直觉的解释（"忙的号被限速了"）当场就站不住：越忙越快，越闲越慢。于是问题变成：那我们到底在测什么？

## 二、第一层：面板日志里的第一个坑

面板有一列叫「首字延迟」。拿它和上游网关的逐单日志一对：

| 来源 | 值 |
|---|---|
| 面板 `first_token_ms` | **124,990 ms** |
| 上游 `TTFB` | **1,480 ms** |

同一笔请求，差了 **123.5 秒**。

不是谁记错了，是量了两件事：

- 上游 TTFB = **第一个数据块**到达的时间；
- 面板的「首字」= 第一个**含正文或推理内容**的 delta。

有些模型在推理阶段一帧内容都不发，等想完了才一次性吐正文。于是「上游 1.5 秒就开始回话」被记成了「首字等了 125 秒」。

**教训一：一个指标的名字，比它的数值更重要。** 叫「首字」却按「首内容」记，下游所有基于它的判断都会歪。

这件事后来变成了一个 PR：给日志加一列 `first_frame_ms`（首个可用 `data:` 帧），和 `first_token_ms` 并存，前者对齐 TTFB，后者仍然表示"正文开始"。

## 三、第二层：`tok / latency` 是个陷阱

有了逐单日志，第一个想法是：

```
吞吐 = completion_tokens / latency
```

于是得到一张很漂亮的二分图：一批号 110–150 tok/s，另一批 35–45 tok/s，而且**同一分钟里并存**。看起来"按账号限速"已经实锤了。

但它有个致命问题：**分母含等待**。

一笔请求：等 1.5 秒（TTFB）+ 生成 3 秒，总共 300 个 token。
- 用 `tok / latency`：**46 tok/s**
- 用 `tok / (latency − TTFB)`：**150 tok/s**

短回复 + 高 TTFB 的场景下，这个误差能到 **3 倍**。

我按正确的口径重算了一遍 1,128 条样本：

| 分组 | n | `tok/latency` | `tok/(latency−TTFB)` |
|---|---|---|---|
| 有首字时间戳 | 278（24.6%） | 116.4 | **242.2** |
| 首字缺失 | 836（**74.1%**） | 117.7 | 算不出来 |

也就是说：**四分之三的样本根本算不出解码速度**——它们连一个增量帧都没有。

**教训二：先确认分母，再谈结论。** 一个指标只要分母里混进了别的阶段，它就不配叫"速度"。

## 四、第三层：自己造一个探针

日志到此为止。想看"每一帧什么时候到"，只能自己发请求。

探针的做法：固定载荷、固定参数、流式请求，**逐 chunk 打时间戳**。

第一版用了 `readline()` 逐行读——结果算出 500 甚至 1000 字/秒，明显不可能。原因是 HTTP 响应有缓冲：上游攒的一大块数据到达后，我在几十毫秒内把里面几百行全"读"完了，**时间跨度被压扁，分母变成假的**。

改成 `read1()`（有多少取多少，不等凑满缓冲）之后：

```
10:07:11  ttfb=1265ms  chunks=61   frames=59   ct=58   →  254 tok/s
10:07:25  ttfb=1527ms  chunks=100  frames=98   ct=300  →   75.6 tok/s
10:08:01  ttfb=14204ms chunks=102  frames=100  ct=300  →   74.4 tok/s
```

三条信息同时成立：

1. 探针测的 TTFB 和上游日志**误差 <30ms**（1265 vs 1262），说明测量可信；
2. `chunks ≈ frames`（1.02），说明**逐帧到达，没有攒包**；
3. 那条等了 **14.2 秒**的请求，一旦开始解码是 **74.4 tok/s**——和正常号的 75.6 几乎一样。

**所以它是"等得久"，不是"吐得慢"。** 这两种慢，处置方式完全相反：前者该换号，后者才该降权。

## 五、我错了五次

诚实记录，因为下面每一条都是真实花掉的时间：

1. **把 `tok/latency` 当吞吐**，差点得出"40 tok/s 是账号属性"的结论。
2. **用 `readline()` 计时**，算出 500 字/秒，被一句"体感根本没这么快"当场戳穿。
3. **说"UA 全空是弱信号"**。实际空值会拼成三段式 UA，改不改没区别——查了源码才发现。
4. **看 8 轮探针 6 轮落在慢号上，就说"几乎全部被限速"**。全池中位其实是 203。
5. **把 `request_logs.ts` 当成请求开始时间**。它其实是**完成时刻**（日志在流结束后才写），所有按时间分桶的分析都整体偏移了一个请求时长。

第 4 条尤其值得记住：**采样偏差会伪装成结论**。我的探针有一半用完全相同的提示词，会话粘性把它全钉在同一个号上——连续四轮都是它，看起来就是"全部都慢"。

## 六、结论：一个"慢"字，三种病

把三层数据对齐之后，能分出三类：

| 类型 | 特征 | 处置 |
|---|---|---|
| **等待慢** | TTFB 高（几秒到十几秒），解码正常 | 换号 / 扩容 |
| **解码慢** | TTFB 正常，解码掉到 1/4 | 降权、避开 |
| **无增量帧** | 首字缺失，整体 tok/s 假性变低 | 当成缓冲问题，不能当慢号 |

而"解码慢"这一类，实测特征如下：

- **持续几小时**：某个号连续 4–5 小时稳定在 71–80 tok/s（样本 90+），然后自己恢复；
- **会换号**：今天上午是 A，下午变 B，晚上又是 C；
- **与上下文长度无关**：按 prompt 分桶（798 条），3 万到 40 万 token 的速率中位都在 117–148；
- **与余额无关**：2358 积分的号在慢档，2351 积分的号在快档，差 2.7 倍；
- **单次不可判**：同一个号 11 分钟里能从 52 跳到 252。

最后这条直接决定了产品设计：**健康度必须用滑动窗口 + 相对基准，不能用单次采样，也不能用绝对值。**

## 七、没解决的部分

- 触发条件看不到。这是云端行为，本地只有观测面。
- 三个身份头里有两个改不了（按 uid 哈希派生），一个造不出来（SDK 签发）。
- 粘性会让一段长会话整段钉在慢号上——池子里还有 5 个 200 tok/s 的号，用户一个都用不到。**这是"体感比统计更差"的根源。**

## 八、可以复用的方法清单

如果下次遇到"某个下游服务时快时慢"，按这个顺序走：

1. **先问"快慢"的定义**：分母是什么？含不含等待？
2. **拿到两端的时间戳**：客户端视角 + 服务端视角，误差能互校才发现口径问题。
3. **固定载荷复现**：可变载荷只能得到相关性，得不到因果。
4. **用相对基准**：同时间窗内的池内中位，而不是历史绝对值——否则一次整体抖动会让全池被误杀。
5. **用滑动窗口**：单次采样不可判；窗口太短会误杀，太长会迟钝。
6. **分层归因**：等待 / 生成 / 缓冲，三种慢分开统计。
7. **默认只读**：任何会自动改别人系统状态的功能，默认关闭 + dry-run。

## 九、最后

这件事最后有两个结果：

- 数据层：日志多了一列「首帧」，和「首字」并存，上游 TTFB 终于可比；
- 决策层：一套按账号吞吐识别慢号、默认只读、显式执行、带自动恢复的机制。

代码是维护者重写的（我的实现被推翻了两版），但**判断标准被留下了**——哪一列该量什么、判据该用哪个分母、什么情况下不该动。这大概是这类协作里最有意思的部分：**你贡献的不是行数，是一个"以后大家都会这么量"的约定。**

以及一个私人教训：**在下结论之前，先怀疑自己的分母。**

## 附录：怎么复现

**指标口径**

`
ttfb        = 第一个非空 data: 帧到达时刻
decode_tps  = completion_tokens / (末帧到达 − 首帧到达)
              # 分母只含生成段；含等待就变成 tok/latency，会低估 2–3 倍
`

**探针要点**

- 用 `read1()` 读原始字节流，不要用 `readline()`（缓冲会把时间跨度压扁）；
- 每轮载荷带一个随机后缀，否则会话粘性会把样本全锁在同一个号上；
- 记录 `chunks` 与 `frames`：两者接近 = 逐帧到达；帧多块少 = 上游在攒包；
- 归因到账号靠**完成时刻 + 总耗时**去匹配上游逐单行（注意：日志时间戳是**完成时刻**，不是开始时刻）。

**判断阈值**

`
窗口 ≥ 15 分钟 · 样本 ≥ 3 · decode < 池内中位 × 0.6  →  判慢
`

用相对基准而不是绝对值：上游整体抖动时，池内中位会跟着动，不会误杀全池。

**这次用到的数据量**

- 面板日志 1,128 条（按 prompt 分桶、按账号分组）
- 上游逐单日志 1,217 条（20 小时，含 4 次重启）
- 可探针 22 轮（30 秒一轮，九个账号）
